# 設計書规则（提炼版，多项目共用）

来源：本仓库 `payload/.cursor/rules/*.mdc` 与 `payload/docs/ai-native/` 规范。项目差异（系统名、错误码格式、locale、术语辞书、模板）取自 init.sh 生成的本地 project.json（脚本用 `--config` 指定；`projects/cmpf/project.json` 只是只读示例，不能直接用），下文「例：」的值只是示例项目的例子。
原规则是为 Markdown 写的；下面是换成 Excel 后仍然成立的部分 + 对应的 sheet。

## 1. 文档组成（一功能一套）
| MD 文件（原规范） | Excel 中的位置 |
|---|---|
| README.md（機能索引） | 表紙 + 目次 |
| 理解现状摘要.md | 現状分析 |
| 処理フロー詳細.md（新功能推荐必建） | 処理フロー |
| 詳細設計書.md（背景・BR・データ摘要・API/画面一览・权限・风险） | 機能概要 / 業務ルール / 画面一覧 / API一覧 |
| 06_画面設計書/{画面ID}.md（每画面一份） | 每画面一张 sheet（sheet 名＝画面 ID，例：`SCR-...`） |
| 07_API設計書/{API ID}.md（每 API 一份）+ openapi.yaml | 每 API 一张 sheet（sheet 名＝API ID，例：`API-...`；契约正本仍是 openapi.yaml） |
| 08_データモデル.md | テーブル定義 |
| 校验/错误码对照（詳細設計書 §4/§9） | チェック・エラー一覧 |
| SQL 一览 | SQL一覧 |
| 验收标准.md | 受入基準 |
| 要件確認事項.md | 要確認事項 |
| 附录「実装対照」 | 実装対照 |
| 修订履历 | 改訂履歴 |

## 2. 记述规范（設計書記述規範.md，必守）
- 读者是产品、测试、评审、别组开发 → 主文写「什么时候发生什么、数据从哪来变成什么存到哪、边界与禁止」，用业务语言。
- **主文禁止函数名、变量名、ref 名、文件路径的调用链**。代码路径/函数名只放 `実装対照`（和 現状分析）。
- 允许出现的技术名：API path/HTTP、请求响应字段、DB 表/列、画面物理名、UI 组件类型（n-select 等）、错误码、权限常量。
- 每个场景用固定块，顺序固定：**目的 → トリガー → 入力 → 処理（编号步骤：做什么→数据变成什么）→ 出力 → 境界・例外**，可附「関連：BR/AC/API/slide」。画面 sheet 的「実装詳細」、API sheet 的「実装詳細」也用这个结构。
- API 的业务逻辑必须自足（读这一节就能理解端到端行为），禁止只写「详见 Service」。
- OpenAPI 已定义的字段不在 API 设计里重复（除非 openapi 不存在/本次无 openapi，则写全）。

## 3. ID / 命名
- 画面 ID 按 `ids.screen_id`（例：`SCR-{B-xx-xx-xx}`）；API ID 按 `ids.api_id`（例：`API-{B-xx-xx-xx-xx}`）；文书编号格式按 `design.doc_no_format`（例：`B04-G-xxx-DD`）。gen_design_xlsx.py 的 lint 按这两个正则整串检查。
- 业务规则 `BR-01…`；验收 `AC-01…`（可带域前缀 `AC-AV-01`）；API 内步骤 `BL-01…`；SQL `SQL-01…`；风险 `R1…`；待确认 `Q1…`；処理フロー `F-01…`。
- 错误码格式按 `ids.error_code`（例：`XXXX\d{4}-[EIW]`，-I 信息 / -W 警告也要列）；文案以 `i18n.locale_dir` 下正文语言（`i18n.languages` 第一个，例：ja）的 message 为准。
- 记号：○ 必须 / △ 条件必须 / × 不做·不传 / ✅ 已实装 / ⏳ 设计有·未实装（状态列里 △ = 与要件有差异）。

## 4. 追溯（PPT 优先）
- 画面布局、列、按钮、图标、控件形态以 **PPT 为第 1 优先**；06 画面设計書第 2；詳細設計・OpenAPI 第 3；既存代码只作业务逻辑参照，**不得单凭旧代码推断 UI 布局**。
- 每个画面 sheet 表头必须写「要件来源（PPT 文件名 + slide/注釈）」。
- 改修画面必须有「PPT vs 现状」差异表（PPT要素 / PPT要求 / 现状实装 / 冲突 / 计划）。
- PPT 没写、但实装必需的规格要写清：`要件由来：slide X を設計で具体化`（或进 要確認事項）。
- 要件対応表：PPT 每页/每注釈 → 设计位置（sheet/ID）→ 既存代码 → 状态。
- 未实装/与 PPT 有差的项标 ⏳/△，禁止误报完成；与 PPT 矛盾的旧描述直接删除，不并存（纠错过程不写进设计书）。

## 5. 要確認事項
- PPT 与代码对不上、PPT 不明确、范围 TBD → 不自己编，写进 要確認事項：问题 / 选项 / 影响（画面・DB・API・权限）/ **暂定设计立场** / 状态（未回答・回答済）/ 回答・回答日・担当。
- 典型问题：范围、数据挂哪个主键、与既存功能关系、权限沿用还是新设、附件/文件规则。
- 在 BA 答复前，设计书按「暂定立场」写，并在相关位置标注 Q 编号。

## 6. 内容要点（从模板提炼）
- 機能概要：要件摘要（# / 变更 / 目标 / slide）、不在范围（项 / 理由）、实现原则（minimal diff、复用哪些既存 Service/组件、校验单一来源、权限与公司隔离与既存一致）、权限（参照 ACCESS_R_* / 更新 ACCESS_U_* / API 公司 ID 过滤）。
- 現状分析（先做）：表主键与业务键、后端入口、前端入口（views/apis/router/locale）、insert/update 分支、重复检查、权限、公司过滤、类似功能参照、风险、本次变更范围勾选。**只读代码**。
- 画面：概要（目的/入口/布局形态/权限）、布局（ASCII 或 PPT 截图，不写颜色像素）、画面項目（项番/项目/物理名/组件/RW/必须/校验）、遷移、イベント（操作/触发/API/请求要点/成功/失败）、バリデーション（规则/时机/messageKey）、i18n（ja+en，不需要 zh）、PPT差异、実装状態サマリ、実装詳細。
- API：处理概要（1～3 句）、请求/响应、认证（Bearer Keycloak）+ 公司 ID、BL 表（条件/处理/失败）、DB 項目（SELECT 条件；INSERT/UPDATE 字段）、エラー処理（错误码/条件/画面表现）、与其他 API/批处理关系、テスト観点。
- テーブル：列名/型/NULL/默认/说明 + 索引/唯一约束 + Entity/Mapper + 迁移脚本（位置按该项目代码确认）+ 旧数据 NULL 的处理。
- 受入基準：每条都要可测试（通过条件可判定），优先级 Must/Should；非功能：权限、多语言（按 `i18n.languages`，例：ja/en）、错误处理。
- 术语：ja↔en 按 `design.glossary` 指定的术语辞书（CMPF 例：排出量=Emissions、取込=Import、出力=Export、拠点=Site …），同一概念全局统一。

## 7. 流程与评审（workflow.mdc / review.mdc）
- 顺序：理解现状 → 写设计书 → 设计评审 → 功能开发 → 实现评审 → 单元测试 → 联调验收；**设计书 RV 有 Blocker 不得进入实装**；验收标准需 Human Lead 批准。
- 设计书 RV 检查：API path/method 与 07/openapi 一致；字段名/类型/必须一致；校验规则一致；DB 表/列/主键一致；画面事件一致；主键/唯一键与 insert/update 分支正确；error check 粒度与邻近功能同等；逻辑删 vs 物理删与既存一致；权限/公司 ID 过滤一致。
- 新功能文档要同步 `単体テスト項目_{機能}.xlsx`（模板按 `unit_test.template`，`試験観点` sheet 不可改）——由单体 case 负责，设计书只在交付说明里提醒。

## 8. 语言
- 仓库现有 MD：标题/表头/业务术语用日文，说明文多为中文。xlsx 版统一：**sheet 名、表头、ID、记号用日文**；正文默认用日文（日式设计书），用户要求时可用中文；PPT 原文、错误 message、UI 文案保持原文不翻译。
