## 1. 为什么要有本规范

设计书的主要读者是 **产品、测试、设计评审、别组开发**——他们需要的是：

- **什么时候**发生什么
- **数据从哪来、变成什么、存到哪**
- **边界与禁止行为**

主文若写成函数调用清单（`rebuildProcessRows` → `mergeUserRowsIntoFresh`），未读代码的人无法理解，也不应作为验收依据。

**代码路径、函数名** 放在附录或元数据表，供维护者跳转。

## 2. 文档分层（写什么、不写什么）

| 文档 | 主文写什么 | 主文避免写什么 |

## 3. 処理フロー章节的固定结构（必用）

每个场景/规则使用以下块，**顺序固定**：

```markdown
### {编号或标题} {业务说法}

**目的** — 为什么要这一步

**触发** — 用户做什么 / 系统何时自动执行

**输入** — 进入本步时系统已有什么（业务对象，非变量名）

**处理**
1. …
2. …
（每步：做什么 → 数据变成什么）

**输出** — 画面或数据库的结果

**边界** — 异常、分支、禁止（可用表格）
```

可选一行：

```markdown
→ 関連：BR-{xx} · AC-{xx} · [07 API-xxx](./07_API設計書/…)
```

## 4. 実装詳細（§11）写法

画面 MD 的 `§11 実装詳細`、API MD 的 `§10 実装詳細` **必须遵守 §3 结构**。

### ❌ 禁止（主文）

```markdown
`openImportDialog` 调用 `runImportDirtyGate`，内部 `hasStep2Changes` 为 true 时
`requestUnsavedDecision` → `tempSave` → `captureStep2Snapshot` …
```

### ✅ 推荐（主文）

```markdown
**目的** — 打开 Excel 取込前，不丢失或未处理 Step2 未保存编辑。

**触发** — 用户在 Step2 点击「データ取込/出力」。

**处理**
1. 若 Step2 相对进入时无变更，校验 Step1 后打开取込弹窗。
2. 若有变更，提示保存 / 破弃 / 取消：
   - 保存：先一時保存成功，再打开取込；
   - 破弃：恢复进入 Step2 时的表格快照，再打开；
   - 取消：留在 Step2。
```

### 附录（可选 §11.2 或文末）

```markdown
## 実装対照（开发用）

| 业务节 | 前端 | 后端 |
|--------|------|------|
| 取込 dirty 门 | `importExportFlow.ts` | — |
```

## 5. 機能文件夹推荐结构

```
docs/{機能}/
├── README.md
├── 理解现状摘要.md          # 表主键 + 代码入口
├── 処理フロー詳細.md        # ★ 业务语言全流程（新機能推荐必建）
├── 詳細設計書.md            # BR 索引；链到処理フロー詳細
├── 06_画面設計書/
├── 07_API設計書/
└── 验收标准.md
```

**新功能 / 大改业务**：实装前或实装同步创建 `処理フロー詳細.md`。  
**小改**：只改对应 § 节，并更新 BR/AC；纯错字可 `単体Case: N/A`。

## 6. Agent / 人工写设计书时的检查清单

写完或改完 `docs/{機能}/` 后自检：

- [ ] 処理フロー主文是否无函数名堆砌？
- [ ] 每个可测行为是否在処理フロー或 06/07 中有「触发→处理→输出」？
- [ ] API 契约字段是否在 07 / openapi，而非只在代码注释？
- [ ] 画面改修是否仍满足 `ppt-first-ui.mdc`？
- [ ] 行为变更是否同步 `単体テスト項目_{機能}.xlsx`（或注明 N/A）？
- [ ] `詳細設計書` 是否链接到 `処理フロー詳細.md`？

## 8. 迁移旧文档

已有设计书若主文含大段函数名：

1. 将流程段落迁入或合并到 `処理フロー詳細.md`（按 §3 重写）。
2. 原处改为一行链接 + 业务摘要表。
3. 代码对照收拢到附录 A。
